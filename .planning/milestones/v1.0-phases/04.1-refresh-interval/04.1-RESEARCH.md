# Phase 4.1: Wire Configurable Refresh Interval - Research

**Researched:** 2026-03-05
**Domain:** Go Bubble Tea — config propagation, `time.Duration` threading, tick cmd refactoring
**Confidence:** HIGH

## Summary

This phase is a pure config-propagation refactor with no new dependencies. Every moving part already exists: `cfg.RefreshInterval` (type `int`, unit seconds, default 2) is already loaded and passed to `NewRootModel`. The five hardcoded tick durations in `s3/client.go` and `ecs/client.go` just need to be replaced with a `time.Duration` stored on each panel model. The only structural work is adding a `refreshInterval time.Duration` field to both panel `Model` structs and threading it from `NewRootModel` → `NewModel` → tick cmd call sites.

The implementation is fully deterministic: all five change locations are identified by exact file and line. The `time.Duration` conversion (`time.Duration(cfg.RefreshInterval) * time.Second`) happens once, at panel construction time in `identityLoadedMsg` handler inside `internal/ui/model.go` (line 132-133), which is the sole call site for both `NewModel` constructors. No other files need changes.

The global 1-second clock tick (`tickCmd()` in `model.go` line 236) is intentionally excluded — it drives only the status bar clock and must not be altered.

**Primary recommendation:** Add `refreshInterval time.Duration` field to both panel models, update both `NewModel` signatures to accept it, convert `cfg.RefreshInterval` once at `identityLoadedMsg` handling, and pass the converted duration to every tick cmd call site (including `descendIntoSelected` where ECS service/task tickers are started on descent).

No new files or directories. Changes touch exactly 4 existing files:


### Pattern 1: Duration Field on Panel Model

**What:** Store `refreshInterval time.Duration` as a field on the panel `Model` struct. Convert once from `int` seconds at construction time.
**When to use:** Any time a config value needs to flow into tick commands — convert at the boundary, store as the native type.
**Example:**
```go
// In s3/model.go or ecs/model.go Model struct
type Model struct {
    // ... existing fields ...
    refreshInterval time.Duration  // set at construction; used by tick cmds
}

// In NewModel (s3 or ecs)
func NewModel(ctx context.Context, awsCfg aws.Config, width, height int, refreshInterval time.Duration) Model {
    // ...
    return Model{
        // ... existing fields ...
        refreshInterval: refreshInterval,
    }
}
```

### Pattern 2: Parameterize Tick Cmd Functions

**What:** Add a `d time.Duration` parameter to the three ECS tick cmd functions and the one S3 tick cmd function. The function body changes from a hardcoded literal to the parameter.
**When to use:** Any `tea.Tick` call that should be configurable.
**Example:**
```go
// Before (s3/client.go line 133)
func S3RefreshTickCmd() tea.Cmd {
    return tea.Tick(30*time.Second, func(t time.Time) tea.Msg {
        return s3RefreshTickMsg{}
    })
}

// After
func S3RefreshTickCmd(d time.Duration) tea.Cmd {
    return tea.Tick(d, func(t time.Time) tea.Msg {
        return s3RefreshTickMsg{}
    })
}
```

### Pattern 3: Conversion at the `identityLoadedMsg` Boundary

**What:** The single call site where both panel models are constructed is the `identityLoadedMsg` handler in `internal/ui/model.go` (lines 132-133). Convert `cfg.RefreshInterval` (int seconds) to `time.Duration` here and pass to both constructors.
**When to use:** Whenever a config int-seconds value must become a `time.Duration` — do it once at the construction boundary, never scatter `time.Duration(n) * time.Second` across call sites.
**Example:**
```go
// In model.go identityLoadedMsg handler
refreshInterval := time.Duration(m.cfg.RefreshInterval) * time.Second
m.s3Panel = s3panel.NewModel(m.ctx, m.awsCfg, m.width, contentH, refreshInterval)
m.ecsPanel = ecspanel.NewModel(m.ctx, m.awsCfg, m.width, contentH, refreshInterval)
```

### Pattern 4: ECS Descent Tick Cmd Propagation

**What:** The ECS `descendIntoSelected` method starts `ECSServiceRefreshTickCmd()` and `ECSTaskRefreshTickCmd()` on descent (Phase 4 decision). These calls must pass `m.refreshInterval`.
**When to use:** Any tick cmd started from within the model's own methods (not just `Init`).
**Example:**
```go
// In ecs/model.go descendIntoSelected — panelClusterList case (line ~514)
return m, tea.Batch(
    cmd,
    FetchServicesCmd(m.ctx, m.client, m.selectedCluster),
    ECSServiceRefreshTickCmd(m.refreshInterval),  // was: ECSServiceRefreshTickCmd()
)

// panelServiceList case (line ~527)
return m, tea.Batch(
    cmd,
    FetchTasksCmd(m.ctx, m.client, m.selectedCluster, serviceArn),
    ECSTaskRefreshTickCmd(m.refreshInterval),      // was: ECSTaskRefreshTickCmd()
)
```

### Pattern 5: Tick Message Handlers Re-schedule with Stored Duration

**What:** Each tick message handler re-schedules the next tick by calling the tick cmd again. After parameterization these calls must also pass `m.refreshInterval`.
**Example:**
```go
// ecs/model.go ecsClusterRefreshTickMsg handler (was: ECSClusterRefreshTickCmd())
return m, tea.Batch(cmd, ECSClusterRefreshTickCmd(m.refreshInterval))

// ecs/model.go ecsServiceRefreshTickMsg handler
return m, ECSServiceRefreshTickCmd(m.refreshInterval)

// ecs/model.go ecsTaskRefreshTickMsg handler
return m, ECSTaskRefreshTickCmd(m.refreshInterval)

// s3/model.go s3RefreshTickMsg handler
return m, tea.Batch(refreshCmd, S3RefreshTickCmd(m.refreshInterval))
```

### Anti-Patterns to Avoid

- **Converting int to Duration at every call site:** Produces scattered `time.Duration(x) * time.Second` expressions and risks inconsistency. Convert once in `identityLoadedMsg`.
- **Changing the 1-second global clock tick:** `tickCmd()` in `model.go` drives the status bar clock and must stay at `time.Second`. Do not touch it.
- **Adding ECS Init re-schedule with interval before model has it:** `Init()` is called immediately after `NewModel` returns, so `m.refreshInterval` is already set at that point — safe to use.
- **Forgetting `descendIntoSelected` tick starts:** The service and task tickers start on descent, not in `Init`. They are started at `ecs/model.go` panelClusterList case (~line 514) and panelServiceList case (~line 527). Both need the parameterized cmd call.

## Common Pitfalls

### Pitfall 1: Missing the `descendIntoSelected` Tick Call Sites
**What goes wrong:** Service and task tickers are started on descent into a cluster or service respectively — not in `Init`. Updating only `Init` leaves two tick cmd calls still hardcoded.
**Why it happens:** `Init` is the obvious place to look. The on-descent tick starts are at `ecs/model.go` lines ~514 and ~527 inside `descendIntoSelected`.
**How to avoid:** After updating `Init`, grep for all remaining `ECSServiceRefreshTickCmd()` and `ECSTaskRefreshTickCmd()` calls in `ecs/model.go` — there are two more in `descendIntoSelected`.
**Warning signs:** Tests pass but tickers revert to hardcoded 10s/5s after first descent.

### Pitfall 2: Tick Message Handlers Re-schedule Without Duration
**What goes wrong:** `ecsClusterRefreshTickMsg` / `ecsServiceRefreshTickMsg` / `ecsTaskRefreshTickMsg` / `s3RefreshTickMsg` handlers all re-schedule the next tick by calling the tick cmd at the end of their handler. Forgetting to pass `m.refreshInterval` there causes tickers to use the zero value (instant re-fire) after the first tick.
**Why it happens:** There are two uses of each tick cmd function: one in `Init`/`descendIntoSelected` and one at the end of each handler.
**How to avoid:** Update all call sites of each tick cmd function simultaneously. Count: `S3RefreshTickCmd` has 2 call sites (Init + handler), `ECSClusterRefreshTickCmd` has 2 (Init + handler), `ECSServiceRefreshTickCmd` has 3 (descendIntoSelected + handler + handler re-schedule), `ECSTaskRefreshTickCmd` has 3 (descendIntoSelected + handler + handler re-schedule).
**Warning signs:** App freezes on first refresh or refreshes extremely rapidly.

### Pitfall 3: `time.Duration` Zero Value If Field Not Initialized
**What goes wrong:** If `NewModel` is called without the `refreshInterval` parameter being passed (e.g., an existing test helper `makeModel` that bypasses `NewModel`), the field defaults to zero. `tea.Tick(0, ...)` fires immediately and continuously.
**Why it happens:** Go zero values; test helpers that construct `Model` structs directly bypass `NewModel`.
**How to avoid:** The `s3/model_test.go` `makeModel` helper constructs a `Model` struct directly (not via `NewModel`). Its tick cmd functions are never called (no `Init` in unit tests), so zero value is harmless in tests. No fix needed, but be aware.
**Warning signs:** Only relevant in production if `NewModel` is called without the parameter — compile error prevents this after signature change.

### Pitfall 4: `go vet` / Compile Errors from Signature Change Cascade
**What goes wrong:** Changing `NewModel` signatures and tick cmd function signatures produces compile errors at all call sites that were not updated.
**Why it happens:** Go's strong typing catches every missed update — this is intentional and helpful.
**How to avoid:** Do a full `go build ./...` after each file's changes. Fix all compile errors before proceeding.
**Warning signs:** `go build` output lists all remaining stale call sites.
