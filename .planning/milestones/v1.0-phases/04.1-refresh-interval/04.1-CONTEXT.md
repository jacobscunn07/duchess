# Phase 4.1: Wire Configurable Refresh Interval - Context

**Gathered:** 2026-03-05
**Status:** Ready for planning

<domain>
## Phase Boundary

Thread `cfg.RefreshInterval` through `NewRootModel` into `s3panel.NewModel` and `ecspanel.NewModel`, replacing all 5 hardcoded tick durations so that `--refresh-interval` and the `refresh_interval:` config key have observable runtime effect. No new user-facing features — this is pure config propagation.

</domain>

<decisions>
## Implementation Decisions

### Ticker unification
- All 5 hardcoded durations (S3: 30s; ECS clusters/services: 10s; ECS tasks: 5s) are replaced by `cfg.RefreshInterval`
- The 1-second global clock tick in rootModel (`tickMsg`) is NOT changed — it drives the status bar clock only
- All ECS sub-tickers (cluster, service, task) use the same uniform `cfg.RefreshInterval`

### Input validation
- Claude's Discretion: no minimum validation required at this phase; trust user input

### Type storage
- Claude's Discretion: store as `time.Duration` in panel models (convert once from `int` seconds at construction)

</decisions>

## Existing Code Insights

### Hardcoded durations to replace (5 total)
- `internal/ui/s3/client.go:133` — `tea.Tick(30*time.Second, ...)` → `S3RefreshTickCmd()`
- `internal/ui/ecs/client.go:214` — `tea.Tick(10*time.Second, ...)` → `ECSClusterRefreshTickCmd()`
- `internal/ui/ecs/client.go:222` — `tea.Tick(10*time.Second, ...)` → `ECSServiceRefreshTickCmd()`
- `internal/ui/ecs/client.go:231` — `tea.Tick(5*time.Second, ...)` → `ECSTaskRefreshTickCmd()`
- `internal/ui/model.go:236` — `tea.Tick(time.Second, ...)` → global clock, DO NOT CHANGE

### Current panel construction (rootModel.go ~line 132)
```go
m.s3Panel = s3panel.NewModel(m.ctx, m.awsCfg, m.width, contentH)
m.ecsPanel = ecspanel.NewModel(m.ctx, m.awsCfg, m.width, contentH)
```
Both need a new `refreshInterval time.Duration` parameter.

### Config already wired
- `cfg.RefreshInterval` is `int` (seconds), default 2
- `NewRootModel(ctx, cfg)` already receives `*config.Config`
- rootModel must store or forward the interval to panel constructors

### ECS descent pattern (Phase 4 decision)
- Service and task tickers started on descent (not in Init) via `m.descendIntoSelected()`
- These re-call `ECSServiceRefreshTickCmd()` and `ECSTaskRefreshTickCmd()` — must pass interval there too

### Reusable patterns
- All async commands follow the `FetchXxxCmd` pattern in `client.go` — tick commands live there too
- Panel models store state as fields; adding `refreshInterval time.Duration` field follows existing pattern

### Integration points
- `cmd/root.go` → `ui.NewRootModel` → `s3panel.NewModel` / `ecspanel.NewModel` → tick cmd functions
